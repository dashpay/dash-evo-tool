# Migration fixtures

A **migration fixture** is a captured Dash Evo Tool data directory, produced by
one specific released build, packed as an archive, and replayed later against a
newer build to prove that upgrading does not lose or corrupt local data.

The fixture is the *input* of the migration matrix. It is never generated by
the current build: it must come from the old binary itself, because the whole
point is to exercise the on-disk shapes that binary actually wrote — schema
version, table set, blob encodings, vault format, config keys.

Nothing in this directory contains a fixture payload. The archives live outside
git as GitHub Actions build artifacts; [`manifest.json`](manifest.json) is the
only durable, version-controlled pointer to them.

## Why this exists

DET has three independent migration mechanisms, and a fixture exercises all
three in the order a real user hits them:

1. The `data.db` read-only contract. Since the platform-wallet rewrite (#860)
   every boot opens an existing `data.db` read-only, and the schema ladder
   (`src/database/initialization.rs`) only builds a fresh file, so a fixture's
   `data.db` must come out byte-identical.
2. The one-shot "unwire" drain of legacy `data.db` rows into the
   `platform-wallet-storage` k/v store, gated by
   `MIN_DIRECT_MIGRATION_VERSION` / `MAX_DIRECT_MIGRATION_VERSION`
   (`src/model/data_migration.rs`).
3. The `refinery` migrations inside `platform-wallet-storage`, shared by
   `det-app.sqlite` and `det-<network>.sqlite`, plus the compatibility bridge in
   `src/wallet_backend/platform_compatibility/` that converts databases written
   by the previously pinned upstream lineage.

The bridge's own tests use synthetic upstream schemas rather than a profile a
real binary wrote. Fixtures close exactly that gap. See
[`docs/ai-design/2026-09-10-migration-matrix/design.md`](../../docs/ai-design/2026-09-10-migration-matrix/design.md)
for the full design and its relationship to PR #981.

## Threat model — read before capturing anything

A fixture archive is uploaded to CI and downloaded by every future matrix run.
Treat every byte in it as **published**.

- **The fixture wallet is public by design.** Its recovery phrase, its
  encrypted seed, its addresses and its identity are all recoverable by anyone
  who can read the artifact. That is accepted, not mitigated.
- **Use a dedicated wallet.** Never reuse the backend-E2E framework wallet
  (`E2E_WALLET_MNEMONIC`) or any wallet that holds funds you care about.
  A funded wallet whose seed is published is a wallet that will be drained.
- **Testnet only.** No fixture is ever captured on mainnet, at any profile.
- **Dust only.** Keep the fixture wallet's balance at the minimum the capture
  needs (enough for the identity registration performed by the *current* build
  when the profile requires one). Sweep anything above that back out. A fixture
  wallet is not a faucet and must never become a place funds accumulate.
- **The recovery phrase is still never committed.** Even though it is public by
  design, it does not go into this repository — not into `manifest.json`, not
  into a profile checklist, not into a scenario file, and not into a commit
  message. Capture reads it at run time from `MIGRATION_FIXTURE_MNEMONIC`
  (protected wallet: `MIGRATION_FIXTURE_PROTECTED_MNEMONIC`), matching the
  `tests/backend-e2e/` convention of referring to environment variable *names*
  only.
- **The protected wallet's password is a fixed literal:
  `correct horse battery staple`.** It is written down here on purpose, the
  same way `PROTECTED_PASSWORD` in
  `src/backend_task/migration/v093_upgrade.rs` and the synthetic rows in
  `src/wallet_backend/platform_compatibility/fixtures/` are: it guards a
  published seed with no value behind it, and a harness that must assert
  "wrong password is rejected, right password still opens the wallet" needs a
  password it can supply deterministically. Its secrecy is not a security
  property of anything.
- **If a fixture wallet is ever funded beyond dust, or is ever used on
  mainnet, it is burned.** Abandon it, mint a fresh one, and recapture. Do not
  try to reclaim it.

## Storage model

Fixture archives are stored as **GitHub Actions build artifacts**
(`actions/upload-artifact` / `actions/download-artifact`), not as GitHub
Release assets.

Consequences that any workflow consuming this directory must handle:

- **Artifacts expire.** The repository default is bounded (typically 90 days).
  A baseline that has to survive every future matrix run therefore needs an
  explicit, long `retention-days` and/or a periodic refresh job that re-uploads
  the same bytes under a new expiry. A one-shot upload is not durable storage.
- **`manifest.json` is the only durable index.** It records which workflow run
  and which artifact name holds which fixture. If the manifest and the artifact
  disagree, the manifest is the statement of intent and the run is the evidence.
- **A missing or expired artifact must fail loudly.** A matrix job that cannot
  download its input fails; it never silently skips, and it never falls back to
  regenerating the fixture with a current build (which would test nothing).
- **A hand capture reaches Actions storage through
  `.github/workflows/migration-fixture-bootstrap.yml`.** Every `gui` capture,
  the v0.9.3 baseline included, is produced outside CI. Dispatch that workflow
  with the entry's `id` and the base64-encoded archive: it checks the bytes
  against the entry's `sha256` and `bytes`, uploads them as `artifact_name`,
  and prints the `workflow_run_id` and `expires_at` to record. Re-dispatching
  the same bytes before `expires_at` is the refresh path.
- **Artifact name convention:** `migration-fixture-<git_tag>-<profile>` — e.g.
  `migration-fixture-v0.9.3-wallet-identity-dpns`. The template also lives in
  the manifest as `artifact_name_template` so tooling does not re-derive it.

## What goes into an archive

Pack the isolated data directory the capture ran against, with these
exclusions:

| Path | Packed? | Why |
|---|---|---|
| `data.db` (≤ v0.9.3 era) | Yes | The unwire drain and the legacy settings import (network, theme) both read it |
| `det-app.sqlite`, `det-<network>.sqlite` (current era) | Yes | The `platform-wallet-storage` layer under test |
| `secrets/det-secrets.pwsvault` (current era) | Yes | Password-protected wallet assertions need the real vault |
| `.env` | Yes | Era-correct config keys are part of what migrates |
| `backups/` | No | Written by the migration itself; packing it pre-seeds the outcome |
| `spv/` and other chain caches | No | Large, re-derivable, and not migration state |
| `det.log`, `det-stderr.log`, `*.log` | No | Noise; may embed host paths |

Archive as `tar.zst` (or `tar.gz` where `zstd` is not available on the runner),
rooted at the data directory itself so extraction reproduces it verbatim,
preserving mode bits — the secret store refuses to open a data directory whose
ancestor chain is group- or other-writable.

Record `sha256` and `bytes` of the finished archive in the manifest entry.

## Capture methods

### `gui` — required for v0.9.3

v0.9.3 predates det-cli, the MCP server and the SPV stack, so there is no
headless entry point at all: the only way to make that binary write its data
directory is to drive the real GUI. It also predates `DASH_EVO_DATA_DIR`
(absent from `src/app_dir.rs` at that tag), so isolation is done with
`XDG_CONFIG_HOME`, and its `.env.example` uses the older key spelling
(`TESTNET_insight_api_url`, `TESTNET_show_in_ui`, `TESTNET_core_zmq_endpoint`,
…) — always copy the one from the tag being captured, never today's.

Step-by-step recipe:
[`docs/gui-testing/scenarios/migration-fixture-capture.md`](../../docs/gui-testing/scenarios/migration-fixture-capture.md).

### `headless` — from the next release forward

Builds that ship det-cli can capture without a display: import the wallet,
derive an address, wait for SPV, and run a tool that triggers identity/DPNS
discovery. Two things still need the GUI until the tooling catches up, and a
manifest entry must say `gui` when either applies:

- Importing a **password-protected** wallet — `core_wallet_import` has no
  password parameter.
- Any capture that has to react to a testnet reset (re-registering an identity,
  re-claiming a name).

## Adding a fixture for a new version

1. **Pick the profile.** See [`profiles/`](profiles/). `wallet-only` is the
   floor; `wallet-identity-dpns` is what the baseline matrix asserts against.
2. **Check the preconditions listed by the profile.** Shared testnet state
   changes underneath you — an identity registered months ago may not survive a
   network reset, and a DPNS name may have been re-registered by someone else.
   Verify with the *current* build before spending time on the old one.
3. **Do the parts the old binary cannot do, with the current build first** —
   for v0.9.3 that means registering the identity and its DPNS name, since that
   binary has no SPV and can only see funds through a local Dash Core node.
4. **Capture with the released binary**, in a fully reset, isolated data
   directory. Never capture two fixtures into the same directory, and never
   capture on top of a directory a previous run touched.
5. **Confirm the profile checklist item by item before quitting the app.**
   Discovery that has not finished yet is the most common way to capture a
   fixture that silently proves nothing.
6. **Quit cleanly** and confirm the process exited before packing — a live
   SQLite WAL sidecar is not a valid fixture.
7. **Pack, upload (`migration-fixture-bootstrap.yml` for a hand capture), and
   add the manifest entry** with the real `workflow_run_id`,
   `artifact_name`, `sha256`, `bytes`, `captured_at` and `retention_days`.
8. **Commit the manifest change.** The archive stays out of git.

## `manifest.json` field reference

JSON permits no comments, so the schema is documented here.

Top level:

| Field | Meaning |
|---|---|
| `schema_version` | Integer. Bump when a field's meaning changes; consumers must reject an unknown value rather than guess. |
| `artifact_name_template` | The naming convention for uploaded archives. Tooling substitutes `<git_tag>` and `<profile>`. |
| `fixtures` | Array of fixture entries. |

Per fixture entry:

| Field | Meaning |
|---|---|
| `id` | Stable identifier, `<git_tag>-<profile>`. Used by the harness to select a case. |
| `git_tag` | The tag whose released binary produced the data. |
| `det_version` | The version string that build reports, without the `v` prefix. |
| `capture_method` | `gui` or `headless` — see "Capture methods". |
| `profile` | `wallet-only` or `wallet-identity-dpns`; the matching file in `profiles/` is the acceptance checklist. |
| `network` | Always `testnet` today; the field exists so a future non-testnet case cannot be mistaken for one. |
| `host_platform` | Where the capture ran. Linux x86-64 only in v1; Windows/macOS are an open decision, not an omission. |
| `binary_asset` | The exact release asset downloaded for the capture. Asset naming changed between eras, so it is recorded per fixture rather than derived. |
| `data_dir_env` | The environment variable that isolated the capture: `XDG_CONFIG_HOME` before `DASH_EVO_DATA_DIR` existed, `DASH_EVO_DATA_DIR` afterwards. |
| `capture_scenario` | Repo-relative path of the procedure that produced it, or `null` for a purely scripted headless capture. |
| `captured_at` | RFC 3339 UTC timestamp of the capture, or `null` while unpacked. |
| `artifact` | Where the archive lives; every field is `null` until an upload exists. |
| `notes` | Free text: anything a future reader needs that the fields cannot express. |

`artifact` sub-fields — all `null` until the fixture is actually packed and
uploaded:

| Field | Meaning |
|---|---|
| `workflow_name` | The workflow file that produced the upload. |
| `workflow_run_id` | The run whose artifacts contain the archive. This is the durable coordinate; artifact names repeat across runs. |
| `artifact_name` | Pre-filled from `artifact_name_template`, so the expected name is reviewable before any upload exists. |
| `archive_filename` | The file inside the artifact. |
| `sha256` | Hex digest of the archive. The harness verifies it after download; a mismatch fails the job. |
| `bytes` | Size of the archive, for sanity-checking a truncated download. |
| `retention_days` | The retention explicitly requested at upload. `null` here means "not uploaded yet", never "repository default". |
| `expires_at` | RFC 3339 UTC expiry, so a refresh job can act before an artifact disappears rather than after. |
